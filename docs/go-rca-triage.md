# G2c — Evidence-linked competing hypothesis triage (preview)

This implementation is an **offline, read-only citation gate**. It does **not** independently establish a root cause, verify an Agent action, authenticate an API source, authorize any write, or declare incident recovery. This Go review component is integrated into the development branch; integration does not mean production RCA or remediation readiness.

## Contract

Use the existing Go evidence sources generated by `collect-changes` and `verify-sli` from **the same relevant incident and time window**. The two Go collectors independently obtain Kubernetes rollout history and Prometheus SLI. Do not combine unrelated CI artifacts and imply a single incident.

`review-rca` accepts an untrusted Agent-proposed list of candidate hypotheses:

| Field | Meaning |
| --- | --- |
| `id`, `kind`, `statement` | Candidate identity and hypothesis; `kind` is `DEPLOYMENT_CAUSAL` or `OTHER_CAUSAL` |
| `claimed_status` | Model-generated status; **ignored as an authority** |
| `supporting_refs` | Cited raw-source content digests using `k8s:<sha256>` or `prom:<sha256>` |
| `contradicting_refs` | Conflicting source references, disjoint from supporting citations |

The gate independently decodes the **three raw Kubernetes responses** and the **three raw Prometheus matrices** from the supplied reports, recomputes their SHA-256, and **re-derives the reported Deployment identity, owner-filtered ReplicaSet revisions, change-window relationship, sampled latency, traffic, scrape freshness and SLI status from those raw bytes**. It rejects any conflicting report summary, missing/duplicate/overlapping citations, malformed source shape, incomplete sample grid or mismatched source category. Only then does it return the following bounded verdicts:

- `CORRELATED_NOT_PROVEN`: the **Deployment causal candidate only** cites both Kubernetes and Prometheus, owned revision time overlaps the incident, the reported SLI is unhealthy, and the windows overlap. This is **not** causal proof.
- `CONTESTED`: the candidate cites opposing evidence. It cannot be promoted.
- `UNVERIFIED`: the requirements for correlation are incomplete, disjoint, absent, or unrelated. This cannot be interpreted as refutation of a different root cause.

The outer status is **always** `HUMAN_REVIEW_REQUIRED`, even if the Agent supplied `claimed_status: SUPPORTED`, `CONFIRMED` or `RECOVERED`. The verifier has no `SUPPORTED`/production-release output path.

A valid SHA-256 detects accidental or uncoordinated changes to raw bytes **but is not a cryptographic origin signature**. A malicious party controlling both bytes and digest can forge both. The checker now **does** independently replay summarized SLI status and the change relationship from stored raw responses, but it still **cannot verify the source's live identity or the operator-owned policy/query provenance**. The Prometheus API response does not cryptographically bind its result to the supplied PromQL; a party controlling the report can alter the query label together with the response. The three Kubernetes reads are not an atomic snapshot, and checksums are not signatures. It is **not** a source-authenticated independent RCA adjudicator; the production G2 gate remains **open**.

## G2d — Externally pinned review policy

`review-rca` now **requires** both `--policy FILE` and `--policy-sha256 PIN`, independently obtained from the operator's trusted configuration/approval channel. The checker binds exact Deployment namespace/name/UID, the three PromQL strings in their respective latency/traffic/freshness roles, all SLI thresholds, sample step and window duration. A mismatched policy pin, exact duplicate JSON key, unknown or noncanonical JSON field, differently cased alias or inconsistent source query fails closed as `UNKNOWN` (exit 3, no report). The exact-case guard and adversarial test cases were integrated into development `main` via [PR #43](https://github.com/avaargsh/sre-agent/pull/43) at `b334bbdc45e16d53e1fd3b382fcb1c6cec54baa9`. **Verification debt:** this integration has no corresponding exact-main Actions/check-runs; the repository's own complete Go/Python/kind checks and independent security review remain unverified.

The policy is an explicit flat `sre.rca-policy/v1` JSON object. The contract requires the **exact lowercase snake_case keys** shown below; differently cased aliases are invalid even when a SHA-256 digest is recomputed over the modified bytes. The guard is present in development main; this is an implementation statement, not an assertion of full CI validation, authenticated policy issuance, or production authorization. A policy checksum alone does not authenticate the issuing operator. Example for a particular Deployment UID (replace with a separately observed authoritative UID):

```json
{
  "schema_version": "sre.rca-policy/v1",
  "namespace": "golden-demo",
  "deployment": "checkout-api",
  "deployment_uid": "REPLACE_WITH_REAL_DEPLOYMENT_UID",
  "latency_query": "max(checkout_request_latency_seconds)",
  "traffic_query": "sum(rate(checkout_requests_total[20s]))",
  "age_query": "max(time() - timestamp(checkout_request_latency_seconds))",
  "max_latency_seconds": 0.01,
  "min_traffic_rps": 0.001,
  "max_sample_age_seconds": 10,
  "window_seconds": 20,
  "step_seconds": 5
}
```

The deliberately strict 0.01-second limit is a **test-only threshold** and must not be treated as a production SLO. A production policy must use approved business SLOs and deployment identity.

```bash
# Pin must be provisioned by a trusted operator / approval channel independently
# of the untrusted Agent-proposed claims or any downloaded evidence.
POLICY=/etc/sre/approved-rca-policy.json
EXPECTED_SHA="$(cat /etc/sre/approved-rca-policy.sha256)"
sre-agent review-rca \
  --changes "$CHANGES" --sli "$SLI" \
  --candidates /tmp/rca-candidates.json \
  --policy "$POLICY" --policy-sha256 "$EXPECTED_SHA" \
  --out /tmp/rca-review.json
```

The same-kind CI demo obtains Deployment UID from the test administrator's Kubernetes read, generates a policy, pins it, then tests unchanged source queries, a forged query, forged SLI summaries and a modified policy file. **Generating both policy bytes and their checksum in CI is only a reproducible integration test, not a source-authenticity or signature proof.** Merely recomputing SHA-256 from an untrusted policy file in the verifier process would defeat the pin. No ACP signer or external policy authority is attached yet.

## Example with grounded evidence references

Use real JSON files from the *same* Golden Incident; do not use artifacts from separate kind runs as a cross-source causal demonstration.

```bash
CHANGES=/tmp/change-evidence.json
SLI=/tmp/sli-assessment.json
K8S_REF="k8s:$(jq -r '.sources[1].response_sha256' "$CHANGES")"
PROM_REF="prom:$(jq -r '.evidence[0].response_sha256' "$SLI")"

jq -n --arg k "$K8S_REF" --arg p "$PROM_REF" '[
  {
    id: "h-rollout",
    kind: "DEPLOYMENT_CAUSAL",
    statement: "The recent rollout may have caused latency",
    claimed_status: "SUPPORTED",
    supporting_refs: [$k, $p],
    contradicting_refs: []
  },
  {
    id: "h-database",
    kind: "OTHER_CAUSAL",
    statement: "Database saturation may have caused latency",
    supporting_refs: [$p],
    contradicting_refs: []
  }
]' > /tmp/rca-candidates.json

go run ./cmd/sre-agent review-rca \
  --changes "$CHANGES" --sli "$SLI" \
  --candidates /tmp/rca-candidates.json \
  --policy "$POLICY" --policy-sha256 "$EXPECTED_SHA" \
  --out /tmp/rca-review.json
```

The result creates a new mode-0600 report, with **no Kubernetes or Prometheus write** and no change to the source reports. A broken source SHA, invalid candidate or repeated citation fails closed as `UNKNOWN` (exit code 3, no report). Exit code 0 means **a triage report was created**, not that an RCA was confirmed. Avoid publishing raw evidence bundles without inspecting potential sensitive Kubernetes metadata and Prometheus labels.

## Required follow-up before a production verifier

1. **Independent replay (implemented for stored snapshots):** re-derive change relationship, Deployment UID/Generation, ReplicaSet ownership/revisions and SLI matrix verdict from decoded raw bytes. Remaining: query-range response provenance, immutable policy IDs, signed source identity, cross-source incident binding and robust ambiguous/malformed JSON rejection.
2. **Source authentication:** bind exact queries and sources to a signed or separately trusted Evidence Package, with immutable provenance and redaction.
3. **Policy binding (implemented for operator-supplied files):** enforce an independently supplied SHA-256 pin and the exact target, PromQL and thresholds. Remaining: signature / authenticated policy distribution through ACP, source identity attestation, durable approval epoch and tamper-proof journaling.
4. **Counterexamples and RCA Oracle:** inject real faults and competing change/metric/log/event histories, compare against externally provided ground truth, report false-positive and abstention rates.
5. **ACP authority and Temporal recovery:** separate identity/policy and execution from validation. All write paths remain disabled; the old Python four-repository gate is still a documented historical dependency.
